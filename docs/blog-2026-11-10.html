这两天把 0.2.30 → 0.2.37 全部重做了一遍。起因很直接：测速数字不可信、固定节点连不上、 OpenVPN 出口只有几兆、DNS 被判定泄露。下面按「问题 → 根因 → 改法 → 结果」逐条写， 文末有下载地址与项目仓库。

一句话总结：不是节点慢，是我们在建隧道、算数字、选 DNS 这三件事上都踩了坑。 坑一个个填掉之后，同一批节点的读数与能不能连，终于对得上了。

一、测速：从「数字不可信」到「数字能对上」

1. 单流测速把好节点测成了烂节点

之前用「一条流 + 2 秒窗口」测下载。真机日志里日本家宽节点显示 ≈79 KB/s， 而同一个节点用 speedtest 实测下行 17 Mbps（≈2 MB/s） —— 差了 25 倍。

原因不是节点，是测法：单流在 200–400ms RTT 的跨境链路上会同时被三件事拖死 —— 慢启动、丢一个包窗口就腰斩、以及「窗口 ÷ RTT」的物理上限。speedtest 用的是 4–8 条并发流， 它给的是「这条线路能给多少」，不是「一条流能给多少」。

改法：4 条并发流 + 800ms 预热 + 稳态采样；节点测速、地区测速、兜底路径全部走同一套口径。

2. 又出现了「十几兆/秒」的假高速

换成多流之后，一批韩国节点报出 10–17 MB/s，比桌面版还快 —— 明显不对。 根因是「窗口内总字节 ÷ 窗口时长」这个算法：预热结束时，每条流在本端缓冲里已经攒了几 MB， 这些字节是窗口开始前收到的，却会在窗口前半段被飞快读出来并计入窗口。

改法：每 250ms 采样一次，丢掉前两个区间（排空缓冲 + 慢启动尾巴），其余取中位数。

3. 列表排版：成功不再出现「握手」两个字，但也绝不伪装成功

旧列表把「握手结果」和「速度」分两处存，速度那份是「上次连上它时」的旧值，于是出现过 「握手成功、只有延迟、速度是别人的」这种自相矛盾的行。现在一行只显示一列结果：

状态 显示
握手成功且测到速度 ≈2.0 MB/s · 3214ms
握手成功但下不动数据 测速失败（标红）
握手失败 握手失败（标红）
还没测 未测

二、OpenVPN 出口下行：几兆 → 十几兆 → 几十兆

这是这轮花时间最多的地方，一共四处叠加：

  1. 接收窗口自适应默认是关的。gVisor 的 ModerateRecvBuf 第一句就是 「关着就直接返回」，所以「最大缓冲」设成多少都不生效，窗口永远停在默认值 —— 1 MiB 窗口 / 300ms RTT ≈ 20 Mbps 封顶，正是「几兆到十几兆」的来源。
  2. OpenVPN over TCP 没关 Nagle。协议是「一个 IP 包一次写」，1217 字节小于 MSS， 在 Nagle 眼里是「小段」，高 RTT 下要等 ACK 才发下一段。
  3. 每读一个包就分配 64 KB。下行 1 万包/秒 = 每秒 640 MB 垃圾，GC 直接把吞吐压在几兆。
  4. netstack 一次通知只取一个包。突发时队列越积越多，下行被通知开销摊薄。 现在改成一次排空队列，并把待发队列从 64 加深到 256。

再加一处「先量清楚再优化」：每次启动第一次连 OpenVPN 出口时，先用同一条 WARP 上游量一次它自己的吞吐， 日志里能看到单流/四流两个数。实测结果很关键 —— 

[tunnel] 诊断：WARP 上游自身吞吐 ≈ 36719 KB/s（4 流）   ← 约 294 Mbps
[tunnel] OpenVPN 出口 218.48.52.240 (KR)
[vpn]    出口实测速度 ≈ 854 KB/s                          ← 约 6.8 Mbps

也就是说 WARP 这一层完全不是瓶颈（和单层 WireGuard 测出的 200–700 Mbps 一致）， 问题在它后面那一段：一条长连接 + 高 RTT + 窗口没给足。0.2.37 已经把窗口自适应关掉、 改成固定大窗口（4/8 MiB），并在握手时协商窗口缩放。

三、连接：固定节点总是失败的两个真实原因

1. 系统拒绝给 tun 配地址

日志里四次固定节点都停在同一句： 

IllegalArgumentException: Cannot set address
    at com.android.server.connectivity.Vpn.jniSetAddresses(Native Method)
    at com.android.server.Vpn.establish(Vpn.java:1860)

VPN Gate 下发的是 10.211.x.x，而 10.0.0.0/8 同时是家用宽带和运营商 CGNAT 最常用的网段， 撞上就被系统拒绝；换前缀（/32 → /24 → /16）也一样被拒。

改法：系统 tun 上放 192.0.2.111（RFC 5737 的 TEST-NET-1，任何真实网络都不会分配）， 由引擎在包泵里做一对一地址替换 —— 出去的包把源地址换成节点下发的，回来的再换回来， 节点侧看到的仍是它分配的地址，回程 NAT 照旧。之后又发现 v6 地址 fd00::1 会因为上一个接口残留被拒，于是改成四组候选地址依次尝试（带 v6 / 不带 v6 / 换地址 / 换网段）。

2. 每次启动都在「重新注册」WARP 账号

根因是一处 %v 的笔误：错误包装把「建 tun 失败」这条链切断了， 于是账号重置逻辑把它当成「WARP 账号失效」，两次之后就把好账号删掉、下次重新注册一台设备。

改法：改成 %w 保留错误链；只有「基础 WARP 隧道自身」失败才计入账号失败； 刷新节点失败不再重置账号。

四、DNS 防泄漏 与 本地代理

  • DNS 防泄漏（默认开）：剔除已知的国内公共解析器（阿里 / 114 / DNSPod / 百度等）， 给每个下发的解析器加 /32 主机路由强制走隧道，防「绕过大陆」分流把 DNS 放出去； 没开 IPv6 时也把 ::/0 抓进 tun（fail closed）。 服务器下发的 DNS 里若带私有地址，只保留它 —— 解析器就在出口那台机器上，测试显示的国家自然一致。
  • 本地代理 / 局域网共享：VPN 模式下以前根本不会起监听（判断条件是 netstack 存在， 而系统 VPN 模式的隧道没有 netstack）。现在两种模式都会监听，Psiphon / OpenVPN 出口还会 另开一个面向局域网的端口并链式经出口转发；界面显示的是真实监听地址， 监听在 0.0.0.0 时自动换成手机的局域网 IP。

五、刷新节点：不再「一直失败」

抓取列表要先起一条临时 WARP 隧道。之前只试一种传输，遇到「20 个端点全握手失败」或 「握手成功、数据面不通」就整块功能不可用。现在按 用户选的协议 → awg → wg → masque → masque-h2（TCP/443） 依次退， 每种 15–30 秒，总上限 75 秒；对话框里也会实时显示进度（抓取到哪一步、正在换哪种协议）。

六、赛风地区测速：全部地区都要测

以前是串行（同一进程只能跑一条 Psiphon 隧道），2 分钟预算只够测前 10 个国家。 现在每个地区各起一条独立的 tunnel 实例，4 路并发，27 个国家约 1 分钟全部测完， 进度与结果实时推给界面。

使用小提示

  • 节点列表里的「测延迟 + 速度」是真实 OpenVPN 握手 + 真下载，不建系统 VPN，可以随时中断。
  • 测完按实测速度重排；标红的是真的连不上，不是没测。
  • 固定节点连不上时，日志会写清卡在哪一步（地址被拒 / 握手失败 / 上游起不来），方便定位。
  • 「DNS 防泄漏」开启后，节点出口下解析器在节点那一侧，泄露检测应显示与出口同国。

已知限制（还在做）

  • WARP 直连模式下，出口 IP 常被判成中国、Cloudflare 解析器被判成美国，泄露检测会报「国家不一致」——那是归属地判定，查询本身没有出隧道。
  • OpenVPN 出口的上限仍受「单条长连接 + 高 RTT」限制，距离桌面版（内核 TCP + 批处理）还有差距，下一步做批量 I/O。

以上改动都来自真机日志逐条定位，不是「调大参数碰运气」。遇到问题请附上日志里的 [tunnel] / [probe] / [vpn] 行，定位会快很多。
