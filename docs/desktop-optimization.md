# 桌面版（D:\work\xhwarp）能否复用 Android 这套方案 & 优化说明

> 本文只做说明与评估，**不改桌面版代码**。
> 触发背景：Android 0.2.37 修完「用户态 TCP 窗口」之后，固定韩国节点从几兆提升到 **80 Mbps**，
> 赛风出口同步提升；桌面版同节点此前约 100 Mbps。需要回答两件事：
> ① 我们的方案能不能搬到桌面；② 桌面版还能怎么优化。

---

## 一、两边现在到底是什么架构

读 `D:\work\xhwarp`（warp-client + `XEHN-dev\core`）得到的事实：

| 层 | 桌面版 | Android 版（本项目） |
|---|---|---|
| 系统 tun | **mihomo 内核**渲染 `tun: enable: true / stack: gvisor / auto-route: true` | VpnService.Builder 自建，Go 包泵读写 fd |
| OpenVPN 出口 | mihomo 的 `type: openvpn` 出站 | 自研：mihomo 的 openvpn **客户端库** + 自建净栈 |
| WARP 前置 | mihomo 的 wireguard / masque 出站，MASQUE 侧带 `congestion-controller: bbr` | 自研 netstack（gVisor）+ 自写 bind |
| 应用侧 TCP | wintun（内核）+ mihomo 批处理 | 系统 tun（内核）+ 每包一次 syscall |
| 节点列表/测速 | 自研（`vpngate.go` / `probe_openvpn.go`） | 自研（同一套思路移植） |

一句话：**桌面版把「数据面」交给了 mihomo，Android 版因为只有一个 tun fd，只能自己实现数据面。**

---

## 二、能不能用「我们的方案」替换桌面版的数据面？

**结论：不建议。** 理由按重要性排序：

1. **桌面版现有的数据面更强**。mihomo 的 tun 有批处理、GSO、可选 `stack: system`（Windows 内核栈），
   QUIC 段还能开 BBR；我们自研那条路是「为 Android 单 tun 限制」做的折中，在桌面上是倒退。
2. **地址替换（一对一 NAT）在桌面上没有意义**。那是为了绕开 Android `Vpn.establish()`
   拒绝配置 10.211.x.x 才做的；桌面用 wintun + 内核路由，不存在这个限制。
3. **维护成本翻倍**。桌面已经在用上游内核，换回自研等于把「别人维护的路径」换成「我们维护的路径」。

**可以搬的是「经验」，不是代码**，也就是下面第三节的四条判据 + 第四节清单。

---

## 三、值得抄到桌面版的三条硬经验（与实现无关）

### 1. 测速必须多流 + 稳态采样

- 单流 + 短窗口在这条链路上会低 10–25 倍（手机端实测 79 KB/s vs speedtest 17 Mbps）；
- 「窗口内总字节 ÷ 时长」会被本端接收缓冲里预热阶段的数据灌水（曾出现 17 MB/s 的假高速）；
- 正确做法：4 流 + 预热 + 逐区间采样取中位数。

### 2. 「握手成功」≠「能用」

桌面版的节点判定如果只看握手/端口，就会把「能握手、数据面不通」的节点当成可用。
建议判定顺序：握手 → **隧道内真实下载 256–512 KB** → 才算可用。

### 3. 失败原因要分层，别一锅端

手机端踩过的坑：一次「建 tun 失败」被当成「WARP 账号失效」，两次之后把好账号删了。
规则：**只有基础 WARP 隧道自己失败**才怀疑账号；节点失败只记节点。

## 四、桌面版优化清单（按收益排序，全部是配置/策略级）

> 前提：不改代码，只调 `settings.json` / 渲染出的 mihomo 配置 / 默认策略。

### P0-1 tun 栈做 A/B：`stack: gvisor` → `stack: system`

- 现在渲染的是 `stack: gvisor`。Windows 上 `system` 栈 = 内核 TCP，吞吐通常更高、CPU 更低；
- 做法：加一个隐藏开关或环境变量，同一节点各测一次 speedtest，比较下行与 CPU；
- 风险：`system` 栈对分应用/规则的兼容性略差，需要回归一遍分流规则。

### P0-2 MTU 与节点对齐，避免「TCP 套 TCP」二次分段

- 节点下发 MTU 多是 1500，但外层是 WARP（1280）。tun MTU 若仍是 1500，
  内层报文会被外层再拆一次，包量翻倍；
- 建议 tun MTU 取 **1160–1240**（与 WARP 的 1280 留出封装余量），并让节点侧 `tun-mtu` 与之一致。

### P1-1 WARP 出站优先「带批处理/GSO」与 BBR 的协议

- 渲染配置里 MASQUE/QUIC 出站已经带 `congestion-controller: bbr`；
  确保 OpenVPN 出站的 `dialer-proxy` 指向的就是这类出站，而不是纯 UDP wireguard；
- 判据：同一节点，`dialer-proxy=masque` 与 `=wireguard` 各测一次，取快的。

### P1-2 端点选择看「到节点的可用带宽」，不看握手延迟

- 手机端实测：WARP 上游自身 4 流 36 MB/s（约 294 Mbps），但打同一个韩国节点只有几百 KB/s ——
  说明「WARP 端点延迟低」不等于「这条路对节点快」；
- 建议：候选端点前 3 个各跑一次 1 MB 下载，按实际吞吐排序并缓存 6–24 小时。

### P1-3 `url-test` 不能替代真实测速

- `url-test` 测的是「经该出站访问一个 URL 的耗时」，含 TCP/TLS 握手，落在几十到几百毫秒，
  对「能不能跑满带宽」几乎无信息量；
- 结论：分组排序继续用 `url-test`，但「固定节点/自动选最快」要用真实下载结果。

### P2-1 DNS 策略照搬手机端三条

1. 剔除国内公共解析器（阿里/114/DNSPod/百度）作为**下发**解析器；
2. 给每个下发解析器加 /32 主机路由，保证「绕过大陆」分流下 DNS 仍走隧道；
3. 服务器下发的 DNS 里若有私有地址（10/8 等），只保留它 —— 它和出口同国。

### P2-2 在桌面日志里加两档上游吞吐诊断

```
[diag] WARP 上游 1 流 ≈ A KB/s，4 流 ≈ B KB/s
```

用于回答「是节点慢还是通道慢」。手机端靠这一行定位到了窗口问题，桌面版同样值得有。

## 五、验证方法（别凭感觉）

同一节点、同一时段，跑三组：

| 组 | 测什么 | 期望（本机实测参考） |
|---|---|---|
| A | 只连 WARP，speedtest | 200–700 Mbps |
| B | WARP + 韩国节点，speedtest | 桌面 ~100 Mbps / 手机 ~80 Mbps |
| C | 单流 vs 4 流诊断 | 4 流应显著高于单流；若接近，说明通道被限速 |

判定：B 明显低于 A 是正常的（跨境 + 节点上传）；**B 只有 A 的 1% 才是有 bug**。

---

## 六、明确不做的事

1. 不为了「让泄露检测显示一致」而把 DNS 换成国内解析器 —— 会拿到被污染的地址；
2. 不在 TCP 套 TCP 的场景下调大 MTU（只会增加分段与重传）；
3. 不把「出口实测速度」（512 KB 短测）当最终速度对外展示 —— 它只反映启动段，
   同节点短测 854 KB/s、speedtest 稳定值 80 Mbps，差 90 倍。

---

## 七、如果将来要做「桌面端自研数据面」

只有在下面两种情况下才值得考虑，且应作为独立项目评估：

1. 需要**无管理员权限**运行（只用 SOCKS、不建 tun）—— 此时手机端那套「netstack + 本地 SOCKS」可以直接复用；
2. 需要与 Android 端**完全一致的行为**（同一份测速/选节点/分流代码），减少双端差异成本。

否则，桌面继续用 mihomo 内核 + 本文第四节的配置优化，是收益/成本比最高的路线。
