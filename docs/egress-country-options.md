# 让出口 IP 变成国外：可行性方案（不改代码）

> 需求：WARP 单层（WG / AWG / MASQUE），不挂 OpenVPN、不挂 Psiphon，
> 让出口 IP 落在**日本 / 美国 / 德国 / 荷兰**这类 Cloudflare 边缘。
> 参考对象：edgetunnel / CFNEW。

---

## 一、先把两件事分开

### 1. WARP 的出口是「WARP 专属 NAT 池」，不是边缘服务器

我们日志里出现过的出口 IP：

```
104.28.245.200   104.28.208.136   104.28.192.14   104.28.225.103
```

全在 `104.28.0.0/16` —— 这是 **Cloudflare WARP 的 egress NAT 地址池**。
它有两个特点，决定了「WARP 单层改不了出口国家」：

- **归属地由 CF 注册信息 + geo 库共同决定**：`104.28.x` 的 whois 是美国 Cloudflare，
  但库按「实际使用地」标中国，于是同一个 IP：
  | 检测站 / 库 | 显示 |
  |---|---|
  | ip-api | 中国 |
  | ipinfo / 部分 CDN 检测 | 美国 Cloudflare |
  | `cloudflare.com/cdn-cgi/trace` 的 `loc=` | 中国（CF 自己判的） |
  这正是你说的「有的站显示美国 Cloudflare CDN」——**是判定差异，不是换了国家**。
- **不随接入 colo 变化**：日志里 `colo=LAX`（洛杉矶边缘）时，出口 IP 仍然是
  `104.28.245.200`。WARP 的 egress 是一个全局 NAT 池，接入哪个边缘都从池里出。

所以：**WARP 单层无论怎么调端点、换协议，出口国家都不会变。**

### 2. CFNEW / edgetunnel 的出口为什么在国外

它们不是 WARP，是 **Cloudflare Worker 代理**：

```
客户端 ──(VLESS/Trojan over WS/TLS，连优选 IP)──▶ CF 边缘(colo)
                                                     │ Worker 在该 colo 执行
                                                     ▼
                                          Worker fetch() 出站到目标站
                                          出口 IP = 该 colo 的 CF 服务器 IP
                                          (104.16.x / 172.67.x，geo=US/DE/NL/JP…)
```

关键点：**最后一跳是 Worker，不是你的设备**。Worker 在哪个 colo 跑，
出口就显示哪个国家；而「优选 IP」决定你的客户端连到哪个 colo —— 所以
**优选 IP 确实能挑国家**（这就是 CFNEW 让你换 IP 就换国家的原理）。

对比我们：

| | 最后一跳 | 出口 IP | 能否选国家 |
|---|---|---|---|
| WARP 单层 | CF WARP NAT | `104.28.x`（固定池） | ❌ 不能 |
| Worker 代理（CFNEW） | 边缘服务器上的 Worker | `104.16.x / 172.67.x` | ✅ 能（优选 IP 选 colo） |

### 3. proxyip 是什么（别指望它）

`proxyip` 是 **Worker 回源时的中转**：Worker 自己访问不了被墙的源站时，
把一个「能访问 CF 任意域名」的反代 IP 填进去，让 Worker 经它出去。
它作用于 `Worker → 源站` 这一段，**和客户端出口国家无关**，
也不能帮 WARP 换国家。

## 二、我们客户端现在有什么出站

| 出站 | 出口国家 | 需要什么 |
|---|---|---|
| WARP（wg/awg/masque/masque-x2/wwarp） | 固定 `104.28.x` | 无 |
| VPN Gate OpenVPN 节点 | 节点所在国（家宽/机房） | 节点列表 |
| Psiphon（可指定地区） | 所选地区 | 无 |
| 本地 SOCKS5（出站方向） | — | **目前没有「上游 SOCKS」配置项**，只有本地监听 |

也就是说：**现有的三条出口里，只有 OpenVPN / Psiphon 能换国家**。
要实现「不用它们、出口在国外」，必须新增一种出站。

## 三、三条可行路径（按推荐度）

### 路径 A：接入 Worker 类节点（VLESS / Trojan over WS/TLS + 优选 IP）

**效果**：出口直接是目标国家的 CF 边缘 IP，和 CFNEW 一致；抗封锁好（WS+TLS+优选 IP），
速度取决于你选的 colo。

**要做什么**：
1. 引擎新增一种出站：客户端侧实现 VLESS/Trojan over WebSocket(+TLS) —— 只做「客户端连
   远端、把 IP 包塞进去」这一件事，和现在 OpenVPN 出口的结构一样（包泵 + 系统 tun），
   所以**不需要改数据面**；
2. 加「优选 IP 列表」：一组 `104.16.x.x / 172.67.x.x / 自定义域名`，按延迟排序；
3. 节点来源：自建 Worker（一个 `workers.dev` 子域即可）或用户自填订阅。

**工作量**：中。VLESS/Trojan+WS 客户端 ≈ 800–1500 行 Go（协议本身比 OpenVPN 简单），
外加 UI 一个「节点/订阅」输入框。
**风险**：需要一个 Worker（用户得有 CF 账号）；公共节点不稳定。
**依赖**：CF 账号 + 一个域名（`workers.dev` 免费子域够用）。

### 路径 B：加「上游 SOCKS5 出站」（最省事，但要另一台设备）

**效果**：手机客户端自己不做代理协议，把流量交给一个现成的代理客户端
（电脑/路由器上跑 Clash/CFNEW 的配置），出口由那台设备决定。

**要做什么**：引擎里 `socksPath` 已经支持「链式经一个 SOCKS5 出去」
（Psiphon 出口就是这么做的），只需要把它暴露成用户可配的一项（host:port），
并在建 tun 时用它做出站。改动量最小（≈100 行 + 一个输入框）。

**工作量**：小。
**代价**：需要局域网里常开一台设备；手机离开那个网络就用不了。
**适用**：家里/办公室固定场景，先验证「Worker 出口在国外」是否满足需求。

### 路径 C：整包引入 mihomo 内核

**效果**：直接获得 VLESS/Trojan/Hysteria/TUIC 等全部出站 + 规则分流。
**工作量**：大（我们 `engine/third_party/mihomo` 目前只有 `openvpn` 和 `common`，
没有 adapter/tunnel/listener；要引数万行 + 依赖，APK 体积和启动时间都会涨）。
**风险**：与现有自研数据面（系统 tun + 包泵）职责重叠，需要重新划边界。
**适用**：长期目标，不是这一轮能定的。

### 对比

| 路径 | 出口能选国家 | 工作量 | 依赖 | 建议 |
|---|---|---|---|---|
| A Worker 节点 | ✅ 能（优选 IP 选 colo） | 中 | CF 账号 | **推荐**，和 CFNEW 同源 |
| B 上游 SOCKS | ✅ 能（由对端决定） | 小 | 另一台设备 | 先验证需求 |
| C mihomo 内核 | ✅ 能 | 大 | — | 长期 |

## 四、不改代码现在能做的三件事

1. **确认「是不是真的在国外」**：连上 WARP 后打开
   `https://www.cloudflare.com/cdn-cgi/trace`，看两个字段：
   - `ip=` 出口 IP（我们的会一直是 `104.28.x`）
   - `loc=` CF 判定的国家（WARP 单层通常 `CN`）

   如果 `loc=CN`，那么任何「显示美国」的检测站都只是库差异，实际地区仍是 CN。

2. **换端点碰运气**：`awg` 的端点池是 `8.6.112.x`，`masque` 是 `162.159.198.x`；
   断开重连几次，看 `colo=` 是否变化（日志里会打）。**但出口 IP 不会变**。

3. **用 OpenVPN / Psiphon 过渡**：需要国外出口时，这两条是现成可用的，不做代码改动。

## 五、结论

- **WARP 单层做不到**：出口是 CF 的 WARP NAT 池（`104.28.x`），归属地固定，
  与 colo、协议、优选 IP 都无关。检测站显示「美国 Cloudflare CDN」是 geo 库差异。
- **CFNEW 能做到，是因为它的最后一跳是 Worker**，出口 IP 由 Worker 所在 colo 决定；
  「优选 IP」之所以能换国家，是因为它决定了请求落到哪个 colo。
- 我们这边要实现同样的效果，**必须新增一种 Worker 类出站**（路径 A），
  或者把流量交给已有的代理（路径 B）。
- `proxyip` 只解决「Worker 回源」，和出口国家无关，不要在这上面花时间。

下一步如果你确认要走路径 A，我可以先出一个最小实现方案（只支持 VLESS+WS+TLS、
固定优选 IP 列表），把改动面控制在「新增一个出站 + 一个设置项」。

## 六、速度：为什么现在 OpenVPN / Psiphon 慢，什么方案才能又快又换国家

### 6.1 三条现有出口的天花板

| 出口 | 天花板 | 原因 |
|---|---|---|
| WARP 单层 | **200–700 Mbps**（实测） | CF 自有骨干，接入边缘即出口 |
| VPN Gate OpenVPN | 多数 3–10 Mbps，好节点 30–80 Mbps | ① 志愿者**家宽上传**（不是下载）；② 跨境 + **TCP over TCP**：内层 TCP 的拥塞控制叠在外层 TCP 上，丢一个包两边同时退窗；③ 经过 WARP 再跨境，RTT 60–150ms |
| Psiphon | 1–10 Mbps | 免费**公共中继**，带宽共享、节点质量不可控、还常被限速 |

一句话：**这两条慢不是我们没优化好，是它们的供给方式决定的**（别人家的上传 / 公共免费中继）。
我们 0.2.37 把 OpenVPN 从几兆优化到 80 Mbps 已经是这条路的物理上限附近。

### 6.2 候选方案的速度对比

| 方案 | 出口可选国家 | 典型下行（国内→国外） | 成本 | 客户端工作量 |
|---|---|---|---|---|
| WARP 单层 | ❌ 固定 CN 判定 | 200–700 Mbps | 免费 | 已有 |
| OpenVPN（VPN Gate） | ✅ 节点国 | 3–80 Mbps | 免费 | 已有 |
| Psiphon | ✅ 地区 | 1–10 Mbps | 免费 | 已有 |
| **CF Worker（VLESS+WS+TLS + 优选 IP）** | ✅ 换优选 IP 即换 colo | **30–150 Mbps** | 免费（CF 账号 + workers.dev） | 中 |
| **自建 VPS + Hysteria2 / TUIC（QUIC+BBR）** | ✅ 买哪国 VPS 就是哪国 | **100–500 Mbps** | $3–6/月 | 中 |
| 商业机场订阅 | ✅ | 50–300 Mbps | ¥10–30/月 | 中（要支持订阅协议） |

### 6.3 为什么 Worker 方案比 OpenVPN 快

1. **没有「别人家上传」这一环**：出口是 CF 边缘服务器，带宽按 CF 骨干算，不是志愿者家宽；
2. **跨境段极短**：客户端→CF 边缘（优选 IP，10–40ms）之后，边缘→Worker 走 CF 内网；
3. **仍是 TCP over TCP，但丢包率极低**：内层 TCP 的拥塞控制不会被外层反复打断
   （OpenVPN 那条路上，外层是在公网上跨境，丢包 1–5% 很常见）；
4. **可以优选 IP**：挑延迟低、不丢包的边缘，等于把「入口」这一段优化到最好。

### 6.4 为什么 Hysteria2 最快（但要钱）

QUIC + BBR：**不做 TCP over TCP**，丢包时不退窗，弱网下比 TCP 类协议快 3–10 倍。
代价：必须自己的 VPS（CF Worker 不转发 UDP，做不到），$3–6/月。

### 6.5 建议的落地顺序

1. **先做路径 B（上游 SOCKS，1 天内可验证）**：在电脑上跑一个 CFNEW / Clash 的
   Worker 配置，手机把出站指向它，实测「Worker 出口的速度与国家」是否满足。
   —— 这一步不改协议、只加一个配置项，风险最低。
2. **满足则做路径 A（内置 VLESS+WS+TLS + 优选 IP）**：摆脱第二台设备，
   预期 30–150 Mbps，换优选 IP 即换国家。
3. **要极致速度再评估 Hysteria2**：需要用户自备 VPS，作为「高级选项」，
   不放进默认路径（否则又要维护一套协议 + 一份服务器）。

> 判据：做完路径 A 后，`cdn-cgi/trace` 的 `loc=` 应该变成 US/JP/DE/NL，
> 且 speedtest 下行应显著高于现在 OpenVPN 的 3–10 Mbps。

## 七、实测反转：Worker 比自建 VPS 快，主力应该走 Worker

用户环境：本地 **1000 Mbps**；自有 VPS 跑 Hysteria2 / TUIC 只有 **100–300 Mbps**；
CFNEW / edgetunnel 部署的 Worker **500–600 Mbps**。**以实测为准，主力选 Worker。**

### 7.1 为什么 Hysteria2/TUIC 跑不过 Worker

| 因素 | Worker（优选 IP） | 自建 VPS（Hysteria2/TUIC） |
|---|---|---|
| 出境链路 | 客户端→CF 边缘，CF 与国内运营商有大量对等互联（HK/JP/SG/美西） | 单台 VPS 的回程线路完全取决于机房：普通线路晚高峰能掉到几十兆 |
| 带宽供给 | CF 骨干，按边缘分摊 | 便宜 VPS 多是「共享 1Gbps」，实际保证常只有 100–300 |
| UDP 待遇 | QUIC/HTTP3 也走 UDP，但 CF 边缘有专门优化 | Hysteria2/TUIC **都是 UDP**，部分运营商对 UDP 限速/QoS，TCP 类反而稳 |
| 协议 | VLESS+WS+TLS（TCP） | QUIC+BBR：**只在「丢包严重但带宽足够」时才有优势**；带宽或线路本身封顶时，BBR 救不了 |

结论：**瓶颈是国际出口和 VPS 回程，不是协议。** 继续在 Hysteria2 上调 MTU / 拥塞控制，
收益很小。

### 7.2 VPS 还有没有用？有，但角色变了

- **备份线路**：CF Worker 被墙/被限时切过去；
- **低延迟场景**：SSH、游戏、RDP（延迟比带宽重要）；
- **可控性**：不依赖 CF 的政策（Workers 免费额度与 ToS 对「代理大量流量」是灰色地带）。

想把 VPS 那条拉起来，先做三步诊断（不改协议）：

```bash
# 1) VPS 自己的带宽上限（单线程，排除多线程虚高）
iperf3 -s            # VPS 上
iperf3 -c <vps> -t 20

# 2) 回程线路：是不是 CN2 GIA / 9929 / CMI
nexttrace <你的家宽IP>     # 在 VPS 上执行，看最后一跳

# 3) 同机对比 TCP 与 UDP 协议
#    VLESS+Reality(TCP)  vs  Hysteria2(UDP)，同一个 VPS 各测一次
```

如果 ② 显示普通 163 线路，或 ③ 里 TCP 明显好于 UDP —— 那是线路/UDP 限速问题，
换协议没用，只能换机房或加中转。

### 7.3 因此本项目的最优组合

| 角色 | 方案 | 预期 |
|---|---|---|
| **主力** | CF Worker：VLESS+WS+TLS + 优选 IP（内置到客户端） | 300–600 Mbps，出口可换国家 |
| 备份 | 自有 VPS（Hysteria2 / VLESS+Reality） | 100–300 Mbps（视线路） |
| 临时/验证 | 手机出站指向电脑上的 Clash/CFNEW（上游 SOCKS） | 取决于电脑那条链路 |
| 兜底 | WARP 单层（不换国家但那最快） | 200–700 Mbps |

**下一步的最小实现（路径 A）要素**，不碰现有数据面：

1. 出站协议：VLESS over WebSocket + TLS（443，SNI/Host 可填），后续再加 Trojan；
2. 节点参数：`UUID / 域名或优选 IP / 端口 / ws path / Host / SNI`；
3. 优选 IP 列表：内置 `104.16.x / 172.67.x` 若干 + 允许用户粘贴自定义；
4. 复用现有结构：与 OpenVPN 出口一样「连远端 → 包泵 → 系统 tun」，只是把
   「OpenVPN 协议」换成「VLESS/WS 帧」；
5. UI：一个「节点」输入框（粘贴 `vless://...` 即可），不订阅也能用。

> 注意：Workers 免费额度是「每天 10 万次请求」，长连接只算一次；但 CF 的 ToS 对
> 「用 Workers 转发大量代理流量」是灰色地带，商用/大流量场景请自行评估。

## 八、公共 SOCKS5 池 / 免费 v2rayN 订阅：可行性与代价

两个提法都成立，但**定位完全不同**：一个是「低成本兜底」，一个是「必须引内核」。

### 8.1 先说清楚 `cm-Workers-CheckSocks5` 是什么

它是**检测器**，不是节点源。部署在 Cloudflare Workers 上，支持
`socks5:// http:// https:// turn:// sstp://` 五类代理的批量检测：

- 批量去重、域名解析（CF DoH → Google DoH 回退）、并发验证；
- 返回**出口 IP / 地区 / ASN / 运营商 / 风险标签 / 耗时**；
- 网页端筛选、地图、导出 TXT/CSV。

它**不产生节点**，也**不测速度**（只有响应耗时）。典型用法是：
自备节点源（VPN Gate SSTP、公开 SOCKS 列表）→ 用 Worker 批量筛「当下可用」→
导出 → 交给客户端。所以「用它的结果当节点池」这件事，节点质量完全取决于源。

### 8.2 方案一：公共 SOCKS5 池 + 客户端分组/定时检测/自动切换

**技术可行性：高。** 我们已有的东西能直接复用：

| 已有能力 | 复用点 |
|---|---|
| `socksPath`（Psiphon 出口的链式 SOCKS） | 加一个「上游 SOCKS5」出站 |
| 节点探针 / 失败记忆 / 自动换点 | 改成按「国家分组」的 health check |
| 国家分类与 UI 分组 | 已有 `VpnGateNode` 那套展示逻辑 |

工作量约 **1 周**：

1. 出站：`socks5://[user:pass@]host:port`，建 tun 时用它拨号（不重建 tun 即可切换）；
2. 节点组：同一国家多个节点，组内按实测延迟/可用性排序；
3. 检测：每 N 分钟对当前组做一次轻量探测（走代理取 `cdn-cgi/trace`，校验出口 IP 变化 + `loc`），
   连续失败 2 次切下一个，全组失效再回退到 WARP；
4. UI：粘贴导入、按国家折叠、显示出口 IP/国家/延迟/最近检测时间。

**代价（必须说清）**：

- **速度**：公共 SOCKS 绝大多数 < 5 Mbps，且大量是蜜罐/秒级失效；**达不到你要的 500 Mbps**；
- **安全**：来源不明的 SOCKS 可以做中间人、注入、记录明文；只能算「应急上网」；
- **稳定性**：今天能用的列表，明天可能全红——必须有 WARP 兜底。

**定位：兜底/应急，不是主力。**

### 8.3 方案二：免费 v2rayN 订阅（VLESS/VMess/Trojan/HY2/TUIC/SS）

**自己实现 6 种协议：不划算。** 粗算：协议 × 传输（ws/grpc/reality/h2/quic/tcp）×
加密/混淆，加上三种订阅格式（Clash YAML / base64 分享链接 / sing-box JSON）的解析、
去重、测速、国家分类 —— 这是 mihomo / sing-box 内核几年的工作量，自研等于重造一遍。

**正确做法：引入 mihomo 内核**（Go 库，gomobile 可绑）：

- 协议与订阅交给内核（`proxy-provider` + `url-test` / `fallback` 策略组）；
- 我们只做：UI、订阅导入、tun fd 接入、把策略组的当前节点显示出来；
- 工作量 **1–2 周**（裁剪、绑定、fd 接入、策略组对接），APK 约 +20–30 MB；
- 风险：与现有自研数据面（系统 tun + 包泵）职责重叠，需要划清边界
  （可以让内核接管 tun，我们保留 WARP / OpenVPN 两条分支做兜底）。

**免费订阅的质量**：比公共 SOCKS 好，但同样「今天 100M、明天全红」，
且来源不明的订阅存在投毒、劫持风险。

### 8.3b 复用电脑版内核（实际路线，工作量 1–2 天）

电脑版（`E:\xiaohe\xhwarp` / `D:\work\xhwarp`）已经是「**mihomo 子进程 + 配置文件 + Clash API**」，
所以不需要重写协议，只要把这条链路搬到 Android：

| 环节 | 电脑版 | Android 上怎么做 |
|---|---|---|
| 内核 | `core/mihomo.exe` 子进程 | 交叉编译成 `android/arm64` 可执行文件，命名 `libmihomo.so` 放 `jniLibs`（Android 10+ 只有 `nativeLibraryDir` 下的文件允许 exec） |
| tun | 系统路由 / wintun | `VpnService.establish()` 拿 fd，配置里写 `tun: { file-descriptor: <fd>, stack: gvisor }`（mihomo 1.19.32 支持该字段） |
| 防环路 | 不需要 | 全局 `interface-name: wlan0/rmnet_data*`（mihomo 支持）把内核出口 socket 绑到物理网卡，否则会被自己的 VPN 抓回去 |
| 控制 | RESTful API | `-ext-ctl-unix /data/.../mihomo.sock`，本地 Unix socket，省掉端口和鉴权 |
| 订阅 / 配置渲染 | `subscribe.go` / `subconfig.go` | 直接复用（提成可绑定的 Go 包，或让 App 侧 Go 引擎调用） |
| 测速 | `subdelay.go`（延迟） | 延迟用 mihomo `/proxies/{name}/delay`（并发、秒级）；**速度**要自己测：对同国家前 5–10 个节点做真实下载 |

关键结论：**没有协议重写，只有「进程 + fd + 网卡绑定」三件事**。
最小链路（能上网）预计半天，接上订阅 + 测速 + 国家分组约 1 天。

测速与分组的口径（与用户共识一致）：

1. 订阅每 30 分钟拉一次（公共订阅本来就高频更新）；
2. 第一层：`delay` 并发筛掉死的（秒级，几百个节点几十秒）；
3. 第二层：同国家的前 N 个做真实下载测速，按**速度**排序（不是延迟）；
4. 每个国家一个 `select` 组（默认指向最快），外加 `fallback` 兜底；
5. 健康检查失败 → 组内顺延，全组失效 → 回退 WARP。

### 8.4 结论与建议的分期

| 期 | 内容 | 工作量 | 能达到什么 |
|---|---|---|---|
| 一期 | 上游 SOCKS5 出站 + 节点组 + 定时检测 + 自动切换 | ~1 周 | 能接公共 SOCKS / 自己电脑上的代理；速度受节点限制 |
| 二期 | VLESS + WS + TLS + 优选 IP（对接你自己的 CF Worker） | ~1–2 周 | **300–600 Mbps，出口可换国家**（你的实测已验证） |
| 三期（可选） | 引入 mihomo 内核，支持免费订阅全协议 | ~1–2 周 | 能用任意订阅，但质量取决于源 |

**推荐：一期 + 二期一起做，二期是主力。** 理由：你的 CF Worker 已经实测 500–600 Mbps，
这是唯一能同时满足「换国家 + 快」的路径；公共 SOCKS 与免费订阅只能补「多节点兜底」，
不能替代主力。

> 安全提醒：公共 SOCKS / 免费订阅来源不可控，建议默认只放行 HTTPS（拒绝明文 HTTP）、
> 在界面明确提示风险，并且永不把它们设为默认出口。
